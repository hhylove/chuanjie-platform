# 创界云枢 V2 多租户 SaaS 架构

> 状态：已评审通过  
> 评审日期：2026-09-09  
> 定位：本文件是 V2 技术架构基线；原始 `.docx` 继续作为业务需求来源。旧版技术实现与本文冲突时，以本文为准。

## 1. 目标与边界

创界云枢建设为多家公司使用的 SaaS 平台。中型规模可直接运行，大型规模可平滑扩展，并支持大客户独立数据库和完整私有部署。

目标容量：

| 阶段 | 租户 | 用户 | 数据量 | 部署重点 |
|---|---:|---:|---:|---|
| 中型 | 约 1,000 家 | 约 10 万 | 约 10 TB | 模块化单体、共享数据库集群、水平扩容 |
| 大型 | 10,000+ 家 | 百万级 | 100 TB+ | Cell 分区、专属数据库、分析存储、容器编排 |

基础可用性目标为 99.9%，RPO 不超过 5 分钟，RTO 不超过 1 小时；大客户可通过专属资源提升至 99.95%。软件架构不依赖必须购买授权的商业模块，但服务器、带宽、短信及第三方平台认证等外部资源可能产生费用。

## 2. 总体形态

```text
内部管理端 / 创业者端 / 供应商端 / 移动端
                    |
             CDN / Nginx / API
                    |
        Java 21 + Spring Boot 模块化单体
                    |
 PostgreSQL 16 / Valkey / SeaweedFS / Outbox Worker
                    |
      监控、日志、备份、第三方集成中心
```

第一阶段不引入微服务、Kubernetes、Kafka 和 OpenSearch。应用保持无状态，可横向增加实例；只有容量、团队或故障隔离指标证明有必要时，才拆为 Cell 或独立服务。

## 3. 租户与身份

### 3.1 控制面与数据面

- 控制面保存全局自然人账号、租户、套餐、期限、配额、模块开关、域名、登录方式、数据库路由和身份服务映射。
- 数据面保存租户业务数据。普通客户进入共享数据库集群，大客户可路由到独立数据库，私有客户部署完整独立环境。
- 同一手机号或邮箱可加入多家公司。用户登录后选择当前租户，并签发包含可信租户上下文的新令牌。
- 请求中的租户编号只能来自已验证会话，不信任前端直接提交的 `tenant_id`。

### 3.2 隔离模型

- 共享表必须包含 `tenant_id`，唯一约束必须包含租户维度。
- MyBatis 租户过滤与 PostgreSQL RLS 双重防护。
- 文件路径使用租户前缀，下载时同时校验租户和业务权限。
- 大客户迁移采用冻结写入、全量复制、增量追平、校验和路由切换，业务代码不改变。

### 3.3 身份认证

- 使用标准 OIDC 身份服务，默认实现为 Casdoor；业务代码不得依赖 Casdoor 专有 SDK。
- 接入手机号/邮箱、微信、企业微信、钉钉、飞书/Lark、LDAP、OIDC、SAML 和 MFA。
- Casdoor只负责认证及外部身份映射；部门、岗位、角色、数据权限和业务授权仍由平台管理。

## 4. 业务模块

| 模块 | 职责 |
|---|---|
| `platform-control` | 全局账号、租户、套餐、配额、模块开关、数据库路由 |
| `tenant-foundation` | 租户成员、组织、岗位、角色、数据权限、字典、编号、审计 |
| `collaboration` | 工作台、审批、任务、日程、文件、通知中心 |
| `project` | 创业者、Project ID、项目、成员、经营单元、协议、风险 |
| `product-supply` | SPU/SKU、选品开发、采购、供应商、仓储、库存、物流 |
| `finance` | 预算、费用、付款、票据、对账、成本、利润、结算 |
| `integration-hub` | 第三方授权、适配器、同步、映射、对账、失败补偿 |
| `analytics-ai` | 指标、报表、预警、知识库、受控 AI 助手 |

模块内部按 Controller → Application Service → Domain → Repository → Mapper 分层。跨模块只能调用公开 API 或领域事件，禁止直接访问其他模块 Mapper。Flowable 只编排审批，不直接修改核心业务表。

## 5. 第三方集成中心

`integration-hub` 统一管理聚水潭、旺店通、电商平台、金蝶/用友、物流、电子发票、支付、身份与消息通道。它负责连接、授权、格式转换和同步，不拥有商品、订单、库存及财务的权威数据。

每个适配器必须具备：

- 租户级凭据加密、授权续期、权限检测和脱敏日志。
- 外部编码映射、原始消息 Inbox、标准化命令/事件和审计轨迹。
- 首次全量、时间游标增量、Webhook、定时对账和断点续传。
- `租户 + 平台 + 外部业务 ID + 版本` 幂等键。
- 限流、指数退避、死信、人工重放和同步状态查询。
- 可配置数据主源及同步方向，防止双向循环覆盖。

聚水潭首期接入商品/SKU、订单、库存和售后，后续扩展采购及财务。第三方故障只暂停对应同步任务，不阻断平台核心业务。初期使用 PostgreSQL Inbox/Outbox 与后台 Worker；达到明确吞吐瓶颈后再引入专用消息队列。

## 6. 通知与短信

`collaboration/notification-center` 决定通知内容、对象、优先级和渠道；`integration-hub` 提供具体通道适配器。支持站内信、邮件、短信、App 推送、微信/公众号、企业微信、钉钉和飞书。

- 默认提供平台公共通道；大客户可配置自有短信、邮件或企业消息账号。
- 业务模块只提交通知命令，禁止直接依赖厂商 SDK。
- 模板、签名、发送记录、回执、重试和退订偏好统一管理。
- 验证码设置有效期、手机号/IP/设备频率限制和防刷策略。
- 重要通知可设置主备通道；普通消息优先使用站内信或低成本通道。
- 短信按条计费属于外部成本，平台不绑定指定供应商，并支持按租户核算用量。

## 7. 数据架构

- PostgreSQL 16 保存事务和主数据；订单、流水、审计等大表按租户与时间分区。
- Valkey用于缓存、会话、验证码、限流和短期锁，不保存唯一永久数据。
- SeaweedFS保存合同、附件和素材，数据库只保存元数据与权限关系。
- 初期报表读取 PostgreSQL 只读副本；数据量达到瓶颈后，将分析数据同步至 ClickHouse。
- 财务、库存、订单等关键写操作必须具备幂等、乐观锁、事务和完整审计。
- PostgreSQL持续归档并定期全量备份，必须定期执行恢复演练。

## 8. 安全与审计

- 权限模型：全局用户 → 租户成员 → 部门/岗位 → 角色 → 功能/数据/字段权限。
- 数据范围支持本人、本部门、本部门及下级、指定范围和全租户。
- 密钥和令牌加密保存，生产密钥不得进入代码仓库，日志自动脱敏。
- 财务、库存、订单、权限、身份绑定及第三方同步均记录操作者、时间、前后值、设备和请求编号。
- 文件使用短期签名地址；正式数据原则上归档或作废，不直接物理删除。
- 支持异常登录告警、会话强制失效、MFA和管理员高风险操作复核。

## 9. 部署与扩展

| 模式 | 应用 | 数据库 | 适用场景 |
|---|---|---|---|
| 标准 SaaS | 共享实例 | 共享集群 | 普通客户 |
| 大客户 | 共享或专属实例 | 独立数据库 | 高隔离、高容量客户 |
| 私有部署 | 客户独立环境 | 客户独立数据库 | 本地化和合规要求 |

三种模式使用同一套源码、镜像和迁移脚本，不建立客户专属代码分支。中型阶段使用 Docker Compose 或常规容器部署；大型阶段按指标引入负载均衡、主从数据库、Cell 分区、消息队列与 Kubernetes。

## 10. 可观测性与故障处理

- Prometheus + Grafana监控延迟、错误率、连接池、慢查询、同步积压、租户用量和备份结果。
- Loki或兼容日志栈按请求编号、租户和业务编号检索日志，但不得记录敏感正文。
- 外部平台超时、限流或不可用时进入重试/死信队列，并向管理员展示同步状态。
- 数据库、对象存储、身份服务和通知通道均需健康检查、超时、熔断及恢复预案。

## 11. 架构决策

| 决策 | 选择 | 主要理由 |
|---|---|---|
| 应用形态 | 模块化单体优先 | 中型可直接运行，维护成本低，保留拆分边界 |
| 主数据库 | PostgreSQL 16 | 事务、RLS、分区、扩展能力成熟 |
| 缓存 | Valkey | 开源许可清晰，兼容 Redis 协议 |
| 文件存储 | SeaweedFS | 可自建、扩展灵活、许可友好 |
| 身份服务 | 标准 OIDC，默认 Casdoor | 中国平台连接能力较好，同时避免专有绑定 |
| 多租户 | 默认共享，大客户独库 | 平衡成本、隔离和扩展性 |
| 异步 | Inbox/Outbox 起步 | 保持简单可靠，按实测容量再引入 MQ |
| 分析 | PostgreSQL 起步，ClickHouse 后置 | 避免过早增加运维组件 |

## 12. 实施门禁

1. 新实现开始前先建立 Git 基线或只读归档，原始需求文档不得删除。
2. V2 阶段骨架、数据库模型、接口契约和验收标准评审通过后才能编码。
3. 每个阶段采用测试先行，租户隔离、权限、幂等、迁移和恢复必须有自动化验证。
4. 删除旧实现须使用明确清单，并在新骨架可构建、可启动后执行。
5. 所有配置、接口、字段和迁移脚本必须写明用途、约束及切换场景。
