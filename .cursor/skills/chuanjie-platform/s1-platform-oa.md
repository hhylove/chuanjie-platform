## 4. 登录与身份（S1-01 核心）

### 4.1 方案（已拍板：JWT）

账号密码登录 + **JWT Access Token**（短时效）+ **Refresh Token**（存 Redis；无 Redis 的 `nodocker` 可用可注释的内存实现或同库降级，配置须说明）。  
前端：`packages/auth` 存 Token；`api-client` 带 `Authorization`；401 统一跳转登录页。  
**不采用** Session / Cookie 会话双轨。

### 4.2 身份类型

| 类型 | 说明 | S1 |
|------|------|----|
| INTERNAL | 内部员工 | 必须可登录 admin-web |
| ENTREPRENEUR | 外部创业者 | 仅枚举/表字段预留 |
| SUPPLIER | 外部供应商 | 仅枚举/表字段预留 |

### 4.3 接口草案（均需 JavaDoc）

| 方法 | 路径 | 用途 |
|------|------|------|
| POST | `/admin-api/v1/auth/login` | 登录；返回 token 与用户摘要 |
| POST | `/admin-api/v1/auth/logout` | 登出；作废 refresh（若有） |
| POST | `/admin-api/v1/auth/refresh` | 刷新 access token（若采用） |
| GET | `/admin-api/v1/auth/me` | 当前用户、角色、权限码、数据范围摘要 |

登录失败须返回明确原因（账号不存在/密码错误/停用），禁止只回「系统异常」。

### 4.4 核心表（草案，字段均 COMMENT）

**`platform_user`**：id、username、password_hash、display_name、mobile、email、user_type、status、dept_id、…审计字段  
**`platform_dept`**：组织树  
**`platform_post`**：岗位  
**`platform_role`**：角色  
**`platform_user_role` / `platform_user_post`**：关联  
**`platform_menu`**：菜单/按钮（permission_code）  
**`platform_role_menu`**：角色菜单  

状态机（用户）：`active` / `disabled`（禁用不可登录）；不物理删除。

**开发种子数据：** 写在 Flyway `V2__platform_identity.sql`（根部门 / ADMIN 角色 / 岗位 / admin 用户），**禁止** Java `ApplicationRunner` 硬编码再插。默认 `admin` / `Admin@123`（BCrypt）。

### 4.5 SSO 预留：Casdoor（仅文档，S1 不编码）

| 项 | 说明 |
|----|------|
| 候选 | [Casdoor](https://github.com/casdoor/casdoor)（Apache 2.0，社区版可商用自托管） |
| 定位 | 未来 **IdP / SSO**（OIDC），尤其企业统一登录、LDAP、S4 创业者/供应商多门户 |
| S1 | **不**加 Compose 服务、**不**引 casdoor SDK、**不**改登录页跳转 Casdoor |
| 与本期关系 | 认证入口本期自建 JWT；业务用户主数据与菜单/数据/字段权限仍在 `platform_*` |
| 日后接入原则 | Casdoor 管「谁登录成功」→ 回调后映射/同步到 `platform_user` → 业务侧签发或换发本系统 JWT（或验 Casdoor JWT + 本地权限装载）；**权限模型不外包给 Casdoor** |
| 表预留（可选，实现时再迁） | `platform_user` 可预留 `external_idp` / `external_subject` 字段 COMMENT 标明「Casdoor 等外部主体映射」；无 Casdoor 时为空 |
| 配置预留（注释占位即可） | 如 `cj.security.sso.enabled=false`、`cj.security.sso.provider=casdoor`（注释写清：关闭时走本地 JWT；开启须另开专项文档与评审） |

**禁止：** 在未改本文件并通过评审前，把 Casdoor 当 S1-01 实现路径。

## 5. 权限（S1-02）

| 层 | 控制 | 实现要点 |
|----|------|----------|
| 功能 | 菜单、路由、按钮 | 后端返回 permission 码；前端 `v-permission`；接口鉴权注解 |
| 数据 | 本人/本部门/本部门及下级/指定项目/全部 | 数据权限维度表 + 查询拦截或 Wrapper |
| 字段 | 成本、利润、薪资等 | 字段权限码；序列化过滤或 VO 分视图 |
| 审计 | 登录、权限变更、敏感查看 | `platform_audit_log` |

S1 先落地：**功能权限 + 数据范围（本人/本部门/全部）**；项目维度数据权限可在 S2 项目模块补齐挂钩。

## 6. 协作与工作台（S1-03 / S1-04 / S1-05）

### 6.1 Flowable

- 引入 Flowable 7；提供 **1 个样例流程**（如「通用审批」：发起 → 直属上级 → 结束）  
- 业务单据只存 `process_instance_id` + **审批态**；业务态另字段  
- API：发起、待办列表、已办、通过、驳回、撤回（按规范校验）

### 6.2 任务与消息

- 任务：标题、处理人、截止、状态、关联业务类型/ID  
- 消息：站内信、已读未读；可与审批待办打通  

### 6.3 工作台

首屏聚合：我的待办（审批+任务）、未读消息、常用入口（可配置）、当前用户信息。  
不做经营大盘（驾驶舱在 S4）。

## 9. 配置与注释

新增配置必须注释用途，例如：

- `cj.security.jwt.secret` / `expire-seconds`：签发密钥与过期时间  
- `cj.security.password.*`：密码策略  
- Flowable 数据源是否复用主库（建议 S1 同库分表前缀 `ACT_`）  

禁止无注释密钥提交；本地用 `application-local.yml` / 环境变量。

## 10. 验收标准（阶段出口）

1. 内部用户可登录 admin-web，错误密码有明确提示  
2. 不同角色看到不同菜单；无权限接口返回业务错误码  
3. 能发起样例审批，在待办中通过/驳回，工作台能看到待办  
4. 用户/角色/菜单变更有审计日志  
5. 相关表字段 COMMENT、接口注释、配置注释齐全  
6. `nodocker` 与 `local` 均可跑通登录（H2/Postgres；JWT secret 配置有注释）
